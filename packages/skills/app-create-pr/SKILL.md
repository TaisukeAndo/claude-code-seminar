# app-create-pr スキル（PR作成Skill）

変更を、PR（プルリクエスト＝「この変更を取り込んでよいか確認してください」という依頼）にして、
利用者が確認できる状態にする。

## 守ること

1. **最初に `.claude/rules/expression-rules.md` を読み、その表現のルールに従う。**
   ファイルがなければ、`app-implement` スキルの `assets/rules/expression-rules.md` を同じ場所にコピーしてよい
2. **マージは行わない。** `gh pr merge` を実行しない。マージ（本番に反映する最後の判断）は、利用者が行う
3. **mainブランチから直接PRを作らない。** 作業用ブランチにいることを確認する
4. **テストでNGが残っているときは、PRを作らず、利用者に伝えて相談する**
5. **個人情報・トークン・`.env` の値を、コミットにもPRの説明にも入れない**

## 手順

### 1. 状態を確認する

1. `git branch --show-current` で、mainではない作業用ブランチにいることを確認する
2. `git status` と `git diff main...HEAD` で、変更の内容を確認する。
   意図しないファイル（`.env`、トークン、大きな生成物、関係のない変更）が入っていないか見る。入っていたら外す
3. `gh auth status` でGitHubにログインできているか確認する。できていなければ、
   利用者に `gh auth login` の実行を案内する（利用者自身のターミナルで行う）

### 2. コミットして、pushする

1. 未コミットの変更があれば、コミットする。メッセージは「何を変えたか」を1行で書く
2. `git push -u origin <ブランチ名>` でGitHubに送る

### 3. PRを作る

`gh pr create --base main` でPRを作る。タイトルと本文は
[references/pr-template.md](references/pr-template.md) の形で書く。
同じブランチのPRがすでにあるときは、新しく作らず、pushだけで更新する（`gh pr view` で確認する）。

### 4. 確認用の環境を確認する

1. `gh pr checks <PR番号>` で、自動処理の結果を見る。実行中なら、終わるまで待つ
   （問い合わせの間隔は長めにする）
2. プレビュー環境の仕組みがあるときは、PRのコメントに出たURLを取り出す（`gh pr view <PR番号> --comments`）。
   **URLは、PRのコメントに出たものだけを伝える。推測で作らない**
3. 自動処理が失敗したときは、ログを読み、原因を「何が起きたか／原因／次にすること」に分けて伝える。
   直せるものは直してpushする

### 5. 利用者に渡す

次を伝える。

- 【進捗】で、PRの作成まで終わったこと
- 何が変わるか（画面でどう見えるか）
- PRのURLと、確認用（プレビュー環境）のURL。パソコンとスマートフォンの両方で開いて確かめてほしいこと
- **【あなたにお願いします】** 確認して問題なければ、GitHubのPRの画面で「Merge pull request」ボタンを押すこと。
  マージすると、自動で本番に反映されるアプリの場合は、その旨を添える
- 直したい点が残っていたら、マージせずに、同じブランチで修正を依頼すること

### 6. マージのあと（利用者が「マージした」と伝えたとき）

1. `git switch main` → `git pull` で最新にする
2. 公開の自動処理があれば、結果を確認する（`gh run list --limit 3`）
3. 本番のURLを開いて、変更が見えることを確認してもらう
