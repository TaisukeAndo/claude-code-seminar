# app-dependency-update スキル（更新Skill）

部品の新しい版のうち、安定していて安全だと確かめられたものだけを上げて、PRにする。
新しい版をすぐに入れないのは、公開直後の版には、不具合や、乗っ取られた作者による不正な版が
含まれていることがあり、数日たつと見つかって取り下げられることが多いため。

## 実行のしかた（2つ）

| 実行のしかた | 見分け方 | 違い |
|---|---|---|
| 定期実行 | 依頼文に「定期実行」と書かれている | 利用者はその場にいない。**質問しない。** 迷うものは見送り、理由を報告に書いて最後まで進める。`app-test` は使わない |
| 手動 | それ以外 | 利用者がその場にいる。最初に、何をするかを短く伝えてから進める。迷うものは利用者に聞いてよい |

## 守ること

1. **最初に `.claude/rules/expression-rules.md` を読み、その表現のルールに従う。**
   無ければ、`app-implement` スキルの `assets/rules/expression-rules.md` を読む。どちらも無ければ、
   専門用語は初めて出たときに一言で説明し、たとえ話を使わず、【進捗】と【あなたにお願いします】を分けて書く
2. **mainブランチに直接コミットしない。マージしない。** 本番への反映は、利用者がPRを確認してから行う
3. **本番環境に触れない。** `wrangler deploy` を実行しない（確認は `--dry-run` まで）
4. **条件を1つでも満たさない版は入れない。** 条件は [references/stability-criteria.md](references/stability-criteria.md)。
   確かめられなかった条件は、満たさないものとして扱う
5. **メジャーバージョンは上げない。** 新しいメジャーがあることだけを報告する
6. **同じ内容のPRを重ねて作らない。** 作業の前に、開いている更新用のPR（このSkillのものと Dependabot のもの）を確認する
7. **PRに、脆弱性の中身を書かない。** PRは公開リポジトリでは誰でも読める。PRには `npm audit` の件数の増減だけを書き、
   今の版に残っている脆弱性のパッケージ名・番号は、PRではなく実行の報告に書く

## 手順

### 1. 準備する

1. `git switch main` → `git pull` で最新にする。未コミットの変更があって切り替えられないときは、止めて報告する
2. 開いている更新用のPRを確認する: `gh api "repos/{owner}/{repo}/pulls?state=open&per_page=100" --jq '.[] | [.head.ref, .title] | @tsv'`。
   ブランチ名が `claude/deps-update` または `dependabot/` で始まるPRがあれば、そのPRで扱っているパッケージは今回の対象から外す。
   （`gh pr` は使わない。クラウドの定期実行では、`gh pr` などGraphQLを使うコマンドが拒否されるため、REST API の `gh api` を使う）
3. 作業用ブランチを作る: `git switch -c claude/deps-update-YYYYMMDD-HHMM`（実行した日時）
4. `npm ci` で、今の版をそろえる。失敗したら、その時点で止めて報告する
5. **更新する前の状態を記録する。** [references/stability-criteria.md](references/stability-criteria.md) の C1〜C4 を一度実行し、
   結果を記録する。C1 は脆弱性の件数（critical・high・moderate）を記録する。
   もともと通らない確認（テストが失敗する、`/api/health` が無いなど）は「元から通らない」と記録し、
   以降の判定から外して、報告に書く

### 2. 新しい版を調べる

`npm outdated --json` で、新しい版があるパッケージを一覧にする。各パッケージについて、
「今の版と同じメジャーバージョンの中で、条件を満たす最も新しい版」を候補にする。

### 3. 候補を1つずつ判定する

[references/stability-criteria.md](references/stability-criteria.md) の S1〜S6 を、候補ごとに確かめる。
1つでも満たさなければ、その候補は見送る（同じメジャーの中に、条件を満たす少し古い版があれば、そちらを候補にしてよい）。

### 4. 1つずつ更新して確かめる

条件を満たした候補ごとに、次を行う。

1. `npm install <パッケージ名>@<版>`（`package.json` の書き方（`^` など）は今のものに合わせる）
2. C1〜C4 を確かめる（手順1.5 で「元から通らない」とした確認は除く）
3. すべて通ったら、そのパッケージだけをコミットする（メッセージ例: `chore(deps): wrangler を 4.150.0 から 4.151.1 に更新`）
4. 1つでも通らなければ、`git checkout -- package.json package-lock.json` → `npm ci` で元に戻し、見送りとして記録する

### 5. PRを作る

1. 1つも更新できなかったときは、PRを作らずに、6 の報告だけを行う
2. 更新できたものがあれば、`git push -u origin <ブランチ名>` でGitHubに送り、REST API でPRを作る。
   PRの本文（下の形）を一時ファイル（例: `/tmp/pr-body.md`。リポジトリの中には置かない）に書き、次を実行する。
   `gh api repos/{owner}/{repo}/pulls -X POST -f title="依存パッケージの更新（YYYY-MM-DD）" -f head=<ブランチ名> -f base=main -F body=@/tmp/pr-body.md --jq .html_url`
   （`app-create-pr` スキルと `gh pr create` は使わない）
3. `gh` が使えない、またはPRを作れなかったときは、ブランチのpushまでで止め、ブランチ名と、PRを作れなかった理由を報告する
4. マージは行わない

```markdown
## 何を更新したか

| パッケージ | 今の版 | 更新後 | 公開された日 | テスト・公開前の確認 |
|---|---|---|---|---|
| wrangler | 4.150.0 | 4.151.1 | 2026-10-28（9日前） | 通過 |

## 見送ったもの

| パッケージ | 新しい版 | 見送った理由 |
|---|---|---|
| hono | 5.0.0 | メジャーバージョンのため。変更点を確かめてから、手動で上げてください |

## どう確かめたか

- 公開から7日以上たっていること、取り下げ・非推奨になっていないこと（npm の情報）
- 更新する版に、既知の脆弱性の報告がないこと（npm audit。使えたときは GitHub Advisory Database・OSV も）
- npm audit の件数: 更新前 critical 0 / high 0 / moderate 1 → 更新後 critical 0 / high 0 / moderate 1
- テスト・公開前の確認（wrangler deploy --dry-run）・起動の確認が通ること
- 元から通らない確認: なし

## あなたにお願いすること

プレビュー環境（あれば）で、主な画面が今までどおり動くか確かめてから、マージしてください。
```

見送った理由に「脆弱性の報告があるため」と書くことはしない（守ること7）。その場合は「条件を満たさないため（詳しくは実行の報告）」と書く。

### 6. 報告する

次を伝える（定期実行のときは、実行結果として残す）。

- 【進捗】で、どこまで終わったか
- 更新したもの・見送ったもの（理由つき。脆弱性の詳細はここに書く）・新しいメジャーバージョンがあるもの
- 元から通らなかった確認と、そのために確かめられなかったこと
- PRのURL（作ったとき）、またはブランチ名とPRを作れなかった理由
- **【あなたにお願いします】** PRを確かめてマージすること。メジャーバージョンを上げるかどうかを決めること

## 定期実行の設定

定期実行の設定方法は [references/schedule-setup.md](references/schedule-setup.md) にある。
利用者に「定期的に実行したい」と言われたら、この手順を案内する。
