# 更新してよい版の条件

## 入れる前の条件（S1〜S6）

| # | 条件 | 確かめ方 | 満たさないとき |
|---|---|---|---|
| S1 | 今の版と同じメジャーバージョンである | 版の先頭の数字を比べる（`4.150.0` → `4.151.1` はよい。`4.x` → `5.0.0` は不可）。`0.x` の版は、2つ目の数字が変わる更新も大きな変更として扱い、見送る | 見送る（新しいメジャーとして報告） |
| S2 | お試し版（プレリリース）ではない | 版に `-alpha`・`-beta`・`-rc`・`-next`・`-canary` などが付いていない | 見送る |
| S3 | 公開から7日以上たっている | `npm view <パッケージ名> time --json` で、その版の公開日時を見る | 7日以上たった、同じメジャーの少し古い版を探す。なければ見送る |
| S4 | 取り下げ・非推奨になっていない | `npm view <パッケージ名>@<版> deprecated` が空 | 見送る |
| S5 | 既知の脆弱性の報告がない | 入れる前に、使えるものだけで確かめる（使えなかったものは「未確認」と記録する）。入れたあとの C1 で、必ず npm audit でも確かめる<br>・GitHub Advisory Database: `gh api "/advisories?ecosystem=npm&affects=<パッケージ名>@<版>"` が空の配列<br>・OSV: `curl -s -X POST https://api.osv.dev/v1/query -d '{"package":{"name":"<パッケージ名>","ecosystem":"npm"},"version":"<版>"}'` が `{}`（`vulns` がない）<br>クラウドの定期実行では、OSV は初期設定の通信許可に入っておらず、`gh api /advisories` も通らないことがある。その場合も、C1 の npm audit（npm の登録所を通るので使える）で確かめられる | 見送る |
| S6 | リリースノートに、破壊的な変更・既知の不具合・取り消しの記載がない | `npm view <パッケージ名> repository.url` からリポジトリを調べ、リリースノートを読む。クラウドの定期実行では、ほかのリポジトリのAPIは拒否されるため読めないことが多い。読めなければ「未確認」と記録して進めてよい | 見送る |

日数（S3の7日）は、利用者が変えてよい。変えたいと言われたら、このファイルの数字を書き換える。

## 入れたあとの確認（C1〜C4）

| # | 確認 | 確かめ方 | 通らないとき |
|---|---|---|---|
| C1 | 新しい脆弱性が増えていない | `npm audit --json` で、①更新したパッケージ自体に脆弱性の報告がない、②件数（critical・high・moderate）が、手順1.5 で記録した更新前の件数より増えていない。`npm audit` が実行できなければ、満たさないものとして扱う | 元に戻して見送る |
| C2 | 自動テストが通る | `package.json` に `test` があれば `npm test` | 元に戻して見送る |
| C3 | 公開の準備が通る | Cloudflare Workers のアプリなら `npx wrangler deploy --dry-run`。`build` があれば `npm run build` | 元に戻して見送る |
| C4 | 自分の環境で起動できる | `npm run dev` などで起動し、`curl` で主なAPI（例: `/api/health`）が応答するかを確かめて止める。手動のときで `app-test` スキルがあれば、それに従ってよい | 元に戻して見送る |

`app-security-check` スキルがあれば、すべての更新が終わったあとに、F（依存パッケージ）の観点だけで点検してもらう。
結果は実行の報告に書き、PRには件数の増減だけを書く（SKILL.md の守ること7）。

C4 で `app-test` を使うのは手動のときだけ。定期実行のときは `curl` での確認にとどめる。
