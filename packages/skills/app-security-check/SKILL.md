# app-security-check スキル（点検Skill）

アプリのリポジトリを読んで、悪用できる弱点がないかを点検し、直す順番がわかる形で報告する。

## 守ること

1. **最初に `.claude/rules/expression-rules.md` を読み、その表現のルールに従う。**
   ファイルがなければ、`app-implement` スキルの `assets/rules/expression-rules.md` を同じ場所にコピーしてよい。
   どちらも無ければ、専門用語は初めて出たときに一言で説明し、たとえ話を使わず、
   【進捗】と【あなたにお願いします】を分けて書く
2. **点検の間は、リポジトリのファイル（コード・`.gitignore` を含む）を書き換えない。** 書いてよいのは `.security-reports/` の中だけ。 直すのは、報告を見た利用者が「直して」と依頼してから
3. **攻撃を実際に送らない。** 本番環境・プレビュー環境に、試しの攻撃リクエストを送らない。
   確かめるのは、コードを読むことと、読み取りだけのコマンド（`git grep`、`npm audit` など）に限る
4. **秘密の値を報告に書き写さない。** 見つけた場所（ファイル名と行番号）だけを書き、値は一部も書かない
5. **報告書をGitHubに上げない。** 弱点の一覧は、公開リポジトリに載ると攻撃の手がかりになる。
   保存先は `.security-reports/` とし、Gitの対象から外す（手順4）。PRの説明にも、弱点の詳しい中身は書かない
6. **確かめられなかった項目は「未確認」と書く。** 推測で「安全です」と言わない
7. **パソコン本体は対象外。** OS・インストール済みのソフト・ファイアウォールの点検を頼まれたら、
   それはこのSkillの対象外であることを伝え、セミナー教材の「パソコンの点検プロンプト」を案内する

## 手順

### 1. アプリの構成をつかむ

最初に `git branch --show-current` で、点検するブランチを記録する。main 以外なら、そのことを利用者に伝える。

`README.md`、`requirements.md`、`package.json`、`wrangler.jsonc`（または `wrangler.toml`）、`src/`、`public/`、
`migrations/` を読み、次をまとめる。

- 画面（`public/` など）と、API（サーバー側。`src/` など）の場所
- データベースの種類と、表の一覧
- ログイン機能の有無と、その方式（なし／Firebase Authentication など）
- 外部サービスとのつながり（APIキーを使うもの）

さらに、APIの一覧を次の表にする。この表が、点検の土台になる。

| 方法 | URL | ログインが必要か | 扱うデータ（誰のデータか） |
|---|---|---|---|
| GET | /api/items | 不要 | 全員分の一覧 |

### 2. 観点ごとに点検する

[references/checklist.md](references/checklist.md) の A〜H の観点を、上から順に点検する。
各項目の「探し方」のコマンドは、読み取りだけのもの。結果は、項目ごとに「問題なし／問題あり／未確認／該当なし」で記録する。

Cloudflare 公式の `workers-best-practices` スキルが入っている場合は、G の観点でその内容も参照する。

### 3. 重さを決める

問題ありの項目を、次の3段階に分ける。迷ったら重い方に入れる。

| 段階 | 意味 |
|---|---|
| 重大 | 今の状態で悪用でき、データの流出・書き換え・なりすまし・不正な課金につながる。公開を止めてでも先に直す |
| 要対応 | 条件がそろうと悪用できる。または、他の人に使ってもらう前に直す必要がある |
| 任意 | 直すと守りが厚くなる。急ぎではない |

### 4. 報告書を作る

1. `.security-reports/` フォルダを作り、その中に `.gitignore` という名前で `*` の1行だけを書いたファイルを置く。
   これで、このフォルダの中のファイルはすべてGitの対象外になる（リポジトリの `.gitignore` は書き換えない）。
   `git status` で、報告書が変更として出てこないことを確かめる。
   あわせて、「リポジトリの `.gitignore` にも `.security-reports/` を入れておくと、より確実です。次にPRを作るときに入れましょう」と利用者に伝える
2. [references/report-template.md](references/report-template.md) の形で、
   `.security-reports/YYYYMMDD-security-check.md` に保存する（日付は実行した日）
3. 利用者には、チャットで次を伝える
   - 【進捗】で、点検が終わったこと
   - 重大・要対応・任意の件数
   - 重大と要対応の各項目を、1行ずつ（何が起きうるか／どこか／直し方）
   - 未確認の項目と、確かめるために必要なこと
   - **【あなたにお願いします】** どの項目から直すかを選ぶこと。おすすめは「重大」から

### 5. 直すとき（利用者が依頼したとき）

1. `app-implement` スキルがあれば、それを使って直す（作業用ブランチ → 修正 → `app-test` → `app-create-pr`）。
   なければ、mainではない作業用ブランチを作って直し、自分のパソコンで動作を確かめてからPRにする
2. 1つの修正で1つの項目を直す。PRの説明に、報告書の項目名と「直したあとの確かめ方」を書く。
   ただし、弱点の詳しい再現方法はPRに書かない（公開リポジトリでは読まれるため）
3. 直したあと、同じ観点だけをもう一度点検し、「問題なし」になったことを報告する

### 6. 呼び出し元から頼まれたとき

`app-dependency-update` スキルから「依存パッケージの観点だけ」と頼まれたときは、F の観点だけを点検し、
結果（新たに増えた脆弱性の有無）を呼び出し元に返す。報告書は作らない。
