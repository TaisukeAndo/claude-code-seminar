# app-builder スキル

アプリ開発の流れ（要件定義→実装→テスト→公開）を、決まった順番で進める。
作業を工程に分けるのは、どの段階で問題が起きたかを切り分け、必要なら前の工程へ戻れるようにするため。

## 守ること（すべての工程で共通）

1. **公開しても問題がない情報だけを扱う。** ログイン認証、顧客の個人情報、社外に出せない情報、
   暗号化が必要なデータが要件に入った場合は、作らずに利用者へ伝え、範囲を絞る提案をする
2. **mainブランチには直接変更を加えない。** 変更のたびに、mainから作業用ブランチを作る
3. **次の操作の前に、必ず利用者の承認を取る。** GitHubへのpush、Cloudflareへのデプロイ、
   D1データベースの作成、GitHubリポジトリの作成。**マージは利用者が行う**（このスキルは行わない）
4. **秘密情報を会話に貼らせない。** APIトークンなどは、GitHubのSecrets設定画面か
   `gh secret set`（対話入力）で、利用者自身が登録する。値を表示・読み取り・ログ出力しない。
   `.env` や `.dev.vars` は `.gitignore` に入れる
5. **説明は [references/plain-language-rules.md](references/plain-language-rules.md) に従う。**
   専門用語は初出で一言説明し、作業の前後に「何をするか／何をしたか」を短く伝える
6. **Cloudflareの仕様は、書く前に公式ドキュメントで確認する。** wranglerの書式、Previews、
   無料枠は変わりやすい。利用者のプロジェクトに入っているwranglerのバージョンと
   `wrangler --help` も確認する（Previewsはwrangler 4.135.0以降が必要）

## 工程0: 作業フォルダを確認する

- 現在のフォルダがアプリ用のリポジトリか確認する。まだなければ、利用者に作成先を確認し、
  新しいフォルダでアプリを始める（`.claude` のSkillやRulesはこのリポジトリの中に置く）
- `git status` で状態を見る。Gitリポジトリでなければ `git init` の承認を取る
- Node.js が使えるか `node -v` で確認する（20以上）

## 工程1: 要件定義

目的: 何を作るかを決め、`requirements.md` に書き出す。実装には進まない。

1. 利用者の困りごと・改善したい作業を聞く。**質問は1問ずつ**行い、まとめて聞かない
2. 次の項目が決まるまで続ける（詳細は [references/requirements-template.md](references/requirements-template.md)）
   - 誰が使うか（自分だけ／社内／一般公開）
   - 何のために使うか（解決したいこと）
   - 扱うデータ（表の項目として書き出す）
   - 画面でできる操作（登録・一覧・編集・削除など）
   - 作らないこと
3. **公開できる範囲か確認する。** 守ること1に当たる項目があれば、ここで範囲を直す
4. 最初に作る機能を1つに絞る（小さく始める）
5. `requirements.md` を書き、利用者に読んでもらって承認を得る。承認までは実装に進まない

## 工程2: 実装

目的: `requirements.md` の「最初の機能」を、動く形で作る。

1. 実装方針（作るファイル、データの表、APIの一覧）を短く説明し、承認を得る
2. mainから作業用ブランチを作る。名前は内容が分かるもの（例: `feature-memo-list`）
3. アプリの土台がなければ [assets/template/](assets/template/) を作業フォルダにコピーして始める
   - 構成: Cloudflare Workers（API＋静的ファイルの配信）＋ D1（データの表）
   - コピーするとき、`gitignore` は `.gitignore` に名前を変える（ドットで始まるファイルは配布時に落ちやすいため、テンプレートでは `gitignore` にしてある）
   - テンプレートの `items` の表・画面は例なので、要件に合わせて書き換える
   - アプリ名・データベース名（`wrangler.jsonc` の `name` / `database_name`）を要件に合わせる
   - `compatibility_date` は、実行環境が対応している過去の日付にする（テンプレートは `2026-10-01`）。
     「今日」を入れると、日本時間の朝などに UTC の日付より先になり、`Compatibility date ... is in the future` で起動しない。
     更新するときは、前日以前の日付にする
4. 表の定義は `migrations/` にSQLファイルとして追加する（既存のファイルは書き換えない）
5. 実装は小さな単位でコミットする。コミットメッセージは「何を変えたか」を1行で書く

## 工程3: テスト（自分のパソコンで確認）

目的: 公開前に、想定どおり動くか確認する。localhostは自分のパソコンからしか開けないので、
公開前に安心して試せる。

1. `npm install` → `npm run db:local`（ローカルのD1に表を作る）→ `npm run dev`（localhostで起動）
2. 起動したアドレス（例: `http://localhost:8787`）を利用者に伝え、ブラウザで開いてもらう
3. [references/test-checklist.md](references/test-checklist.md) の項目を、実際に確認する。
   APIは `curl` でも確認する。結果は「項目／結果／気づいたこと」の一覧で報告する
4. うまく動かない箇所は原因の候補を説明し、直して、もう一度確認する
5. 全項目が確認できるまで、工程4へは進まない

## 工程4: 公開（GitHub → GitHub Actions → Cloudflare）

目的: 確認できた内容をGitHubに保存し、自動でCloudflareに公開する。
詳しい手順と設定は [references/deploy-setup.md](references/deploy-setup.md) に従う。

初回だけ必要な準備（それぞれ承認を取ってから行う）:
1. GitHubにリポジトリを作る（`gh repo create`。公開範囲は利用者に確認する）
2. Cloudflareに本番用と確認用のD1データベースを作り、`wrangler.jsonc` にIDを書く
3. GitHub Secretsに `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を、**利用者自身が**登録する
4. [assets/template/.github/workflows/](assets/template/.github/workflows/) のワークフローを配置する

変更のたびの流れ:
1. 作業ブランチをGitHubへpushする（承認後）
2. PRを作る。説明には「何を変えたか／どう確認したか／プレビュー環境で見てほしい点」を書く
3. PRをきっかけに、確認用の環境（Workers Previews）が自動で作られ、URLがPRにコメントされる。
   パソコンとスマートフォンの両方でこのURLを開いて確認してもらう
4. 問題がなければ**利用者がPRをmainにマージする**。マージをきっかけに本番へ自動デプロイされる
5. 本番のURLを開き、変更が反映されたことを確認する

## 作業が終わったら

- 作ったもの（ブランチ名、PRのURL、確認した項目、本番のURL）を短くまとめて報告する
- 「次に直したい点・足したい機能」を聞き、あれば工程1か工程2に戻る
- このスキルで繰り返す作業は、実装・テスト・PR作成のSkillに分けて自作すると、
  毎回の指示が不要になる（アプリのリポジトリの `.claude/skills/` に置く）
