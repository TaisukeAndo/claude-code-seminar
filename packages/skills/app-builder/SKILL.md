# app-builder スキル

アプリを新しく作るときの流れ（要件定義→実装→テスト→公開）を、決まった順番で、最後まで進める。

- **要件定義で利用者と認識をそろえる。** ここだけは、利用者とやり取りしながら慎重に進める
- **要件と実施計画の承認が取れたら、実装・テスト・公開を、途中で止まらずに一通り作り切る**
- **PRは作らない。** 初回の構築では、mainに直接コミットして公開する。PRとプレビュー環境は、
  公開したあとの運用（変更を加えていく段階）で使う。そのための設定は
  [references/operation-setup.md](references/operation-setup.md) にまとめてある

## 守ること（すべての工程で共通）

1. **公開しても問題がない情報だけを扱う。** ログイン認証、顧客の個人情報、社外に出せない情報、
   暗号化が必要なデータが要件に入った場合は、作らずに利用者へ伝え、範囲を絞る提案をする
2. **外部に何かが作られる操作は、実施計画で承認を得た内容の範囲で行う。** 範囲を超える操作
   （計画にないリポジトリの作成、別のアカウントへの公開など）は、もう一度承認を取る
3. **秘密情報を会話に貼らせない。** APIトークンなどは、GitHubのSecrets設定画面か
   `gh secret set`（対話入力）で、利用者自身が登録する。値を表示・読み取り・ログ出力しない。
   `.env` や `.dev.vars` は `.gitignore` に入れる
4. **説明は [references/plain-language-rules.md](references/plain-language-rules.md) に従う。**
   専門用語は初出で一言説明し、作業の前後に「何をするか／何をしたか」を短く伝える
5. **Cloudflareの仕様は、書く前に公式ドキュメントで確認する。** wranglerの書式、無料枠は
   変わりやすい。利用者のプロジェクトに入っているwranglerのバージョンと `wrangler --help` も確認する。
   Cloudflare上の操作は、まずCloudflare MCPで行い、MCPで足りない部分（表の作成とデプロイは
   GitHub Actions、トークンの作成は利用者）だけ別の手段を使う。
   役割分担は [references/deploy-setup.md](references/deploy-setup.md) の冒頭の表に従う

## 工程0: 作業フォルダを確認する

- 現在のフォルダがアプリ用のリポジトリか確認する。まだなければ、利用者に作成先を確認し、
  新しいフォルダでアプリを始める（`.claude` のSkillやRulesはこのリポジトリの中に置く）
- `git status` で状態を見る。Gitリポジトリでなければ `git init`（ブランチ名は `main`）を行う
- Node.js が使えるか `node -v` で確認する（20以上）

## 工程1: 要件定義（利用者と認識をそろえる）

目的: 何を作るかを決め、`requirements.md` に書き出し、実施計画とあわせて承認を得る。

1. 利用者の困りごと・改善したい作業を聞く。**質問は1問ずつ**行い、まとめて聞かない
2. 次の項目が決まるまで続ける（詳細は [references/requirements-template.md](references/requirements-template.md)）
   - 誰が使うか（自分だけ／社内／一般公開）
   - 何のために使うか（解決したいこと）
   - 扱うデータ（表の項目として書き出す。同じ内容が何行にも出るものは、表を分けてidで参照する形にする）
   - 画面でできる操作（登録・一覧・編集・削除など）
   - 作らないこと
3. **公開できる範囲か確認する。** 守ること1に当たる項目があれば、ここで範囲を直す
4. **今回作る範囲を決める。** 1回で作り切れる大きさにする。大きくなりそうなら、
   「今回作る機能」と「次回以降に回す機能」に分ける（次回以降は、運用の段階で追加する）
5. `requirements.md` を書き、次の **実施計画** とあわせて利用者に見せて、承認を得る。
   **承認までは実装に進まない。承認されたら、以降は工程4の最後まで続けて進める**

実施計画に書くこと:

- 作るもの（画面、API、データの表、機能の一覧）
- 外部に作られるもの（GitHubのリポジトリと公開範囲、Cloudflareの本番用D1データベース、公開されるURL）
- 利用者自身が行うこと（Cloudflareのダッシュボードでの、APIトークンの作成とGitHubへの登録）
- 終わったあとの状態（URLを開けば、パソコンでもスマートフォンでも使える）

## 工程2: 実装（作り切る）

目的: `requirements.md` の「今回作る範囲」を、動く形で作り切る。

1. アプリの土台がなければ [assets/template/](assets/template/) を作業フォルダにコピーして始める
   - 構成: Cloudflare Workers（API＋静的ファイルの配信）＋ D1（データの表）
   - コピーするとき、`gitignore` は `.gitignore` に名前を変える（ドットで始まるファイルは配布時に落ちやすいため、テンプレートでは `gitignore` にしてある）
   - テンプレートの `items` の表・画面は例なので、要件に合わせて書き換える
   - アプリ名・データベース名（`wrangler.jsonc` の `name` / `database_name`）を要件に合わせる
   - `compatibility_date` は、実行環境が対応している過去の日付にする（テンプレートは `2026-10-01`）。
     「今日」を入れると、日本時間の朝などに UTC の日付より先になり、`Compatibility date ... is in the future` で起動しない
2. 表の定義は `migrations/` にSQLファイルとして追加する（既存のファイルは書き換えない）
3. 要件の機能を、すべて実装する。**mainに直接コミットする。** ブランチは切らない
4. 実装は小さな単位でコミットする。コミットメッセージは「何を変えたか」を1行で書く

## 工程3: テスト（自分のパソコンで確認）

目的: 公開前に、想定どおり動くか確認する。localhostは自分のパソコンからしか開けないので、
公開前に安心して試せる。

1. `npm install` → `npm run db:local`（ローカルのD1に表を作る）→ `npm run dev`（localhostで起動）
2. [references/test-checklist.md](references/test-checklist.md) の項目を、実際に確認する。
   APIは `curl` でも確認する。結果は「項目／結果／気づいたこと」の一覧にまとめる
3. うまく動かない箇所は、原因を調べて直し、もう一度確認する。直したらコミットする
4. 全項目が確認できたら、そのまま工程4へ進む。localhostのアドレスは、最後の報告で利用者に伝える

## 工程4: 公開（GitHub → GitHub Actions → Cloudflare）

目的: 作ったアプリをGitHubに保存し、自動でCloudflareに公開する。
詳しい手順と設定は [references/deploy-setup.md](references/deploy-setup.md) に従う。
承認済みの実施計画の範囲で、次の順に進める（順番が大事。トークンの登録の前にpushしない）。

1. **Cloudflare MCP** で、接続とアカウントを確認し、本番用のD1データベースを作り、
   `wrangler.jsonc` にIDを書く（MCPで作れないときだけ `wrangler d1 create`）
2. GitHubにリポジトリを作る（pushはまだしない）
3. **利用者に、APIトークンの作成とGitHubへの登録を依頼する。** 登録の完了を確認するまで待つ。
   アカウントIDは、AIが登録してよい
4. [assets/template/.github/workflows/deploy.yml](assets/template/.github/workflows/deploy.yml) を配置し、
   mainをpushする。GitHub Actionsが、表の作成と本番へのデプロイを行う
5. Actionsが成功したことと、本番のURLで動くことを確認する（Cloudflare MCPで、表ができているかも確認する）

## 作業が終わったら

次を短くまとめて報告する。

- 公開したURL（パソコンとスマートフォンの両方で開いて確認するよう伝える）
- localhostで動かすときのアドレスと、確認した項目の一覧
- 「次回以降に回す機能」があれば、その一覧
- **これからの変更は、PRを使って行う**こと。ブランチを切って実装し、PRを作り、確認してからmainにマージする。
  この流れを毎回の指示なしで行うために、実装・テスト・PR作成のSkillを、アプリのリポジトリの
  `.claude/skills/` に自作する。確認用の環境（Previews）の設定は
  [references/operation-setup.md](references/operation-setup.md) を使う
